01 / FROM SETUP TO YOUR GAME

Start after the first playable run

Complete Getting started first: run Godot with local Nakama, play as a guest, activate the beacon, and restart to confirm progress is saved. Then use this flow for your first meaningful game feature.

One example throughout: rename the beacon. Let the player choose a short name displayed above the existing beacon button. Save it on this device across restarts. Keep accounts and the once-only 10-coin tutorial reward unchanged. This is a proposed example to build in your game; the starter does not already include it.

The template already includes the workflow and command files. Open your game repository in Claude Code or Cursor, start a new chat if needed to discover its commands, and enter:

IN YOUR LLM CHAT / NOT THE TERMINAL
/sdd setup

The assistant checks Node.js 22.13+ or a newer LTS (24+), installs the pinned OpenSpec development tooling if needed, and reports the current specs and active changes. No global OpenSpec installation or account is required.

Expected result: tooling is ready and the assistant lists existing capabilities and active work. Setup does not create rename-beacon or change the game.

Its skill runs the same workflow; replace the /sdd prefix in each example with $mobile-spec-workflow, such as $mobile-spec-workflow implement rename-beacon. All commands and skill requests go to the LLM, which runs terminal tooling internally.

Keep experiments and routine fixes small. Explore uncertain mechanics before promising detailed requirements. A fix with unchanged behavior usually needs focused regression coverage rather than a new set of planning documents.

02 / EXPLORE THE IDEA

Choose a small first version

PASTE INTO YOUR CODING ASSISTANT
/sdd explore Let players rename the example beacon. Compare a name saved only on this device with an account-synced name. Recommend the smallest useful version, keeping the existing tutorial reward unchanged. Do not implement it yet.

Expected result: the assistant compares the persistence choices and explains their tradeoffs. For this walkthrough, choose a device-local name: no new server field or RPC is needed. Exploration does not create the feature plan or edit game code.

03 / DESCRIBE THE OUTCOME

Plan one playable feature

Describe what the player should be able to do. The assistant reads relevant existing specs, asks about material missing decisions, and writes a short proposal, behavior scenarios, design, and task list. Keep the first version to one playable interaction.

PASTE INTO YOUR CODING ASSISTANT
/sdd plan Let the player rename the beacon with a text field and Save button. Show the name above the existing beacon button and save it only on this device across restarts. Trim whitespace and accept 1–24 characters. Empty or longer names must leave the saved name unchanged and show a validation message. Start with "My beacon" when no name is saved. Keep the tutorial reward and account behavior unchanged. Use change name rename-beacon.

Expected result: openspec/changes/rename-beacon/ contains a concise proposal, scenario deltas, design, and tasks. The assistant identifies local persistence, input validation, mobile controls, and verification work. Game code is still unchanged.

Make the result observable

For example: given the saved name is "My beacon", when the player saves " Lighthouse ", the label shows "Lighthouse" and keeps that name after restarting. When an empty name is submitted, the saved name stays unchanged and a validation message appears.

Current behavior stays in openspec/specs/. Proposed changes go in openspec/changes/rename-beacon/, so an unfinished idea does not become the current contract.

04 / BUILD THE FEATURE

Implement the agreed scope

PASTE INTO YOUR CODING ASSISTANT
/sdd implement rename-beacon

Expected result: the game has the name label, input, Save action, validation, and device-local persistence. The existing beacon activation and reward still work. Relevant tests and actual results are recorded with the tasks; implementation alone does not archive the change.

The assistant uses the existing Godot, Nakama, and artwork guidance. If you already asked it to plan and implement, it can continue through both without requesting the same permission again. If the requirements change, update the plan and scenarios explicitly.

05 / CHECK THE RESULT

Verify the same feature

IN YOUR LLM CHAT / CHECK THE RESULT
/sdd verify rename-beacon

Expected result: the assistant reports evidence for the default name, trimming, valid save, rejection of empty/overlong names, restart persistence, touch controls, and the unchanged once-only reward. Required checks that could not run stay open; a structural pass alone does not prove the feature works.

Verification checks the changed requirements against the implementation, runs structural and relevant project checks, and reports actual evidence. It leaves failures visible without silently implementing repairs. Omit the change name when the conversation already selects one; the assistant asks if the selection is ambiguous.

Backend, authentication, or deployment changes also need local up and smoke checks. OpenSpec validation checks document structure; tests and recorded observations establish whether the behavior works. Physical-device runs and signed builds need separate evidence when required.

06 / KEEP THE CONTRACT CURRENT

Finish with evidence

PASTE INTO YOUR CODING ASSISTANT
/sdd finish rename-beacon

Expected result: when required checks pass, the current specs include beacon naming and the completed rename-beacon change moves into the dated archive. If restart persistence or another required check is unverified, the assistant reports it and leaves the change open.

The assistant checks required tasks and evidence before archiving. If required work remains incomplete, it reports what is missing and leaves the change open.

Archiving merges the implemented behavior into current specs and moves the proposal, design, tasks, and evidence into openspec/changes/archive/. It is local bookkeeping; it does not commit, push, deploy, or publish your game.

For future features, repeat this small loop: describe the change, implement the authorized work, verify it, and update the current contract.

The four starter capabilities cover accounts, player state, mobile lifecycle, and framework updates. Adapt these as your game changes. Framework upgrades preserve game-owned specs, configuration, and history; mobile exports exclude them.
