02 / FIRST PLAYABLE RUN

Run your first prototype

Run these commands from your copy of the repository.

Check your tools

Godot 4.7.2, Node.js 22+ with npm, Bash, and a running Docker installation with Compose v2 supporting up --wait.

Missing something? Let your coding assistant guide setup.

TERMINAL / REPOSITORY ROOT
node tools/manage.mjs init
node tools/manage.mjs up
  1. 01

    Create your local configuration

    init creates a private .env with random secrets and generates the public client config. It refuses to overwrite an existing file.

  2. 02

    Start the local backend

    up installs locked backend dependencies, compiles TypeScript, and starts PostgreSQL and Nakama. Wait for the health checks to pass.

  3. 03

    Play the first loop

    Open project.godot, press F5, choose Play as guest → Play, and activate the beacon. You receive 10 coins once. Restart the game to restore the same player.

Already initialized? Skip init. Use up to start services and reload backend changes. Link an email under Account to keep access across installations.

ARCHITECTURE / ACCOUNTS & PROGRESS

Player actions and saved state

The client sends a player action. The backend checks it, updates private storage, and returns the complete saved state. The tutorial shows this process in a working example.

  1. 01 / CLIENTPlayer intentcomplete_tutorial {}
  2. 02 / SERVERValidate & commitOnce-only condition + version check
  3. 03 / CLIENTCanonical stateReplace the local snapshot

The included RPCs

Authenticated server actions
RPCRequestResult
get_state{}Initialize or read the player snapshot.
update_profile{"display_name":"Pilot"}Validate and save the display name.
complete_tutorial{}Complete onboarding and grant 10 coins once.

Successful RPCs return {"state": {...}, "server_time": ...}. Player storage is private, and only the server can write to it. Every mutation checks the stored version. If writes compete, the client may need to read state again.

Sessions, retries, and new rewards

Guest players can link an email without losing their player ID. The wrapper refreshes and saves sessions, restores them on launch, and reads current state when the app resumes. Requests have a 15-second timeout.

SDK automatic refresh and retry are disabled. When a write's outcome is unknown, the client reads state to find out what happened instead of repeating the mutation. A definite HTTP 401 can trigger a session refresh and one retry.

Check new reward conditions on the server. The tutorial grants a bonus when the player acknowledges completion; it cannot prove a win or validate a submitted score. Repeatable purchases or transfers need durable operation receipts, and schema changes need explicit migrations.

Refresh tokens currently live in app-private user://session.cfg. Decide whether your shipped game needs platform Keychain or Keystore storage.

DEVICES / ANDROID & iOS

Export for Android and iOS

The current client starts with a 720 × 1280 portrait layout, large touch controls, and Compatibility rendering. Export helpers use the selected env file for identity, versions, and asset paths.

Android

Install matching Godot export templates and configure the Android SDK and JDK in Godot Editor Settings. Start with a debug APK.

ANDROID / DEBUG APK
node tools/export.mjs --env-file .env android-debug

For an emulator, use http://10.0.2.2:7350 as CLIENT_API_URL. For a physical phone, use your computer's LAN IP, set LOCAL_BIND_IP=0.0.0.0, allow the port through your firewall, and run up. Development HTTP may require a debug-only cleartext policy.

Android release builds

Create a per-game release keystore. Set GODOT_ANDROID_KEYSTORE_RELEASE_PATH, GODOT_ANDROID_KEYSTORE_RELEASE_USER, and GODOT_ANDROID_KEYSTORE_RELEASE_PASSWORD privately in the production env file. Verify your HTTPS backend before exporting.

ANDROID / RELEASE APK
node tools/export.mjs --env-file .env.production android-release

The helper produces an APK. AAB export and store submission require additional per-game setup.

iOS

Use macOS, Xcode, matching Godot templates, an Apple developer team, and a unique bundle ID. Set IOS_TEAM_ID in your chosen env file. Use a valid HTTPS backend.

iOS / XCODE PROJECT
node tools/export.mjs --env-file .env ios-project

This creates an archive containing the Xcode project. Configure signing and provisioning in Xcode, build on a device, then prepare distribution.

Export helpers do not publish or upload your game. Keep signing credentials private. Make preset changes in tools/export_presets.template so they survive the next configure run.

PRODUCTION / BACKEND DEPLOYMENT

Deploy your backend to a VPS

The backend deploys to your own VPS over SSH. PostgreSQL stores player data, Nakama runs your server logic, and Caddy provides automatic HTTPS.

  1. Prepare a dedicated host and path. Install Docker Engine and Compose v2, trust the SSH host key, and create a writable deployment directory. Configure DNS, SSH access, and ports 80/443. An existing reverse proxy needs integration rather than a second listener.
  2. Create separate production configuration. Run the command below, then set your domain, HTTPS client URL, SSH connection, deployment path, and unique game identity locally.
CREATE PRODUCTION CONFIG / FIRST TIME ONLY
node tools/manage.mjs --env-file .env.production init

Set API_DOMAIN, TLS_EMAIL, CLIENT_API_URL, SSH_HOST, SSH_USER, SSH_PORT, and DEPLOY_PATH. Keep LOCAL_BIND_IP=127.0.0.1. The deployment directory must already exist.

  1. Verify locally, then deploy. Pass check and smoke against development. Preserve production secrets and back up existing data before updates.
DEPLOY THE BACKEND TO YOUR CONFIGURED HOST
node tools/manage.mjs --env-file .env.production deploy

Deployment builds the backend locally, uploads compiled code and runtime configuration, and waits for the database and Nakama health checks to pass. Verify the public https://YOUR_DOMAIN/healthcheck endpoint and an exported client separately.

Configuration boundaries and recovery

Only api_url, public server_key, and game_title enter client/config.json. Server credentials stay out of client exports. Configuration comes from the selected env file. Do not source it as shell code.

Deployment briefly restarts Nakama and is not atomic. Keep the previous Git revision and a tested database backup available. The script saves the previous env configuration as .env.previous. A database migration may require restoring a backup.

Redeploy with the same project name, deployment path, and secrets to retain data. Never delete volumes as a troubleshooting shortcut. Access the admin console through an SSH tunnel.

After deployment, generated client config points to production. Run local configure to switch back to development.

RELEASE / KNOW WHAT IS LEFT

What to check before release

Before release, test your game on devices, verify the production backend, and complete the store requirements.

  • Test a clean install, guest play, email linking, login on another installation, logout, and account deletion.
  • Check touch, safe areas, the keyboard, small screens, background/resume, audio, and haptics on real devices.
  • Test interrupted writes, duplicate requests, session expiry, and migrations without losing saves.
  • Verify public HTTPS, backup restoration, signing, provisioning, and store requirements.

The starter needs an online connection to load player state before play. Offline queues, realtime multiplayer, analytics, purchases, ads, push notifications, social login, email verification, and password-reset email delivery are not included.

Local checks have covered the API, SDK, navigation, and infrastructure. Android/iOS device runs and a public VPS deployment still need separate verification. See the verification record for results and remaining checks.

HELP / QUESTIONS & FIXES

Common questions

Is this tied to one game engine?

The name leaves room for other engines, but the current kit uses a Godot client with Nakama and TypeScript. To use another engine, you need to replace the client integration and export tools.

Can I use the prototype as the starting point for a shipped game?

Yes, that is the intended path. Keep the accounts, saved state, settings, and deployment tools as you build out the game. You still need to review security and dependency licenses, prepare production operations, test on devices, and meet store requirements. The starter alone does not make a game ready for production.

Why can I open the app but not enter the game?

The menu opens after the client authenticates and loads player state. Check that Docker is running, run node tools/manage.mjs status, and inspect logs. Confirm the selected env file has the correct CLIENT_API_URL, then run up.

Why did my phone fail to connect?

Your phone's localhost is the phone itself. Use the computer's LAN address, put both on the same network, set LOCAL_BIND_IP=0.0.0.0, allow the API port through the firewall, and run up. The Android emulator can use 10.0.2.2. Use HTTPS for production and iOS.

Will stopping Docker delete progress?

node tools/manage.mjs down stops services and preserves database volumes. Keep the same Compose project name to reconnect to the same data. Do not use docker compose down -v unless you explicitly intend to delete data.

What should I do after changing configuration or server code?

Run configure after changing the title, identity, endpoint, or export inputs. Run up after backend edits to rebuild and reload Nakama. Run check and the relevant live smoke tests before deploying.
